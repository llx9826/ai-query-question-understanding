# 原生上下文与人员查询输出修复

2026-09-15 · AgentScope 2.0.8 · Plan v1.14

本批已完成两项修复：问题理解读取原生会话中的双方消息和实际查询结果；查询人员时返回可读姓名，极值查询保留并列对象。最终6项真实模型回归通过，181项自动测试通过。没有改业务数据库、模型型号、前端或数据准备模块。

## 根因

1. 自定义 QueryAgent 覆盖 reply_stream 后没有完整维护原生上下文。原代码只把用户消息加入 AgentState.context，且每轮裁到8条；助手回答没有写入该上下文。
2. 理解适配器直接调用模型，输入只有自行投影的业务状态。last_successful_result_ref只是追踪编号，模型无法凭它得知SQL返回了谁。
3. SQL提示没有明确规定人员结果的可读身份及极值并列口径。“谁参加的活动最多”曾只返回一个报名ID。独立查询真实Excel库确认，有34条报名记录并列最多12项。
4. 第一版接入历史后，复测发现模型仍可能回答上一轮：本轮请求埋在大量背景JSON中。最终把背景、原生历史和本轮原话分开，最后一条user消息固定为本轮实际问题。保留第一版失败记录，不把它当作通过。

## 职责与实现

| 位置 | 本批工作 |
|---|---|
| 原生会话接线 app/orchestration | 用 Agent.observe 接收用户消息，用 AgentState.append_context 保存实际结果和助手回答；由既有原生SQLite存储保存恢复；移除只保留8条用户消息的截断 |
| 上下文配置 | 调用公开 Agent.compress_context，复用 ContextConfig 和原生summary；短会话仅本地计数，不调用摘要模型 |
| 问题理解 | 固定输入增加history、history_summary、last_result；节点仍接受纯DTO，可独立回放，不依赖Agent对象或存储 |
| 结果指代 | 模型选择真实结果行号；classify_outcome核对来源轮次、有效范围和重复行，再将选中结构化结果传给SQL模块；不伪造用户姓名原话 |
| 查询执行 | SQL提示明确人员姓名、活动名称、同名身份区分和极值并列；查询前校验结果引用的数据快照版本 |

保留六个业务模块，修改的业务模块仅question_understanding、query_execution；另外修改编排接线和共享结果契约。没有独立建立第二套聊天记录库，原生AgentState.context与summary负责对话历史。原有SavedQuery仍是查询结果检查点，供解释重试及本轮结构化输入使用，新增turn_id防止失败的新查询错误继承旧成功结果。

理解模型的实际消息顺序为：系统规则 → 语义目录与本轮可用背景 → 原生历史消息 → 本轮用户原话。历史回答及SQL结果视为数据，不能覆盖系统规则。框架的私有方法没有被调用或修改。

结果上下文最多投影50行、16000字符行数据，超预算省略整行，不截短姓名或ID；明确标记截断，完整结果仍在查询检查点。空结果、失败结果、跨范围或跨版本结果不能冒充本轮可用对象。

## 验收

最终真实测试通过当前/ui-api入口，使用百炼实际模型、AgentScope原生会话和原始Excel SQLite，问题之间有真实应用重启：

| 编号 | 场景 | 核验结果 | 模型调用 |
|---|---|---|---:|
| R1 | 谁参加的活动最多 | 34名并列者，姓名和活动次数与独立SQL逐项一致，均12项 | 3 |
| R2 | 他是谁啊 | 多人结果下明确要求选择，不擅自挑一人 | 1 |
| R3 | 那第一位是谁，叫什么名字、哪个公司 | PAOLO SEMILIA，R.Star S.p.A.，与该次结果第一行一致 | 3 |
| R4 | 重启后问他参加哪些活动 | 返回同一人的12项活动，与独立SQL逐项一致 | 3 |
| L1 | 从只有ID4692的结果重启后追问他是谁 | FARZAD SALEHIMARANI，品牌O&J，公司Omoda & Jaecoo Canada Inc. | 3 |
| L2 | 再追问他是哪个品牌 | O&J，身份没有切换 | 3 |

L0是前置复现场景：按用户贴出的ID-only形状，在真实数据库查询ID4692的12项活动计数，通过受控SQL输出端口写入原生会话；它没有调用真实模型，不算进6项真实模型成绩，也不是虚构业务数据。L1、L2均使用真实模型。

最终共16次模型调用，0次额外摘要或评审调用，0次审计写入异常。全部SQL可重放，根请求和阶段审计完整，网页进度均报告完成。模型输入记录确认每次最后一条消息是本轮用户原话。最终应用代码与测试冻结哈希完全一致。

自动测试181项通过，覆盖消息双向保存、独立模块/节点、重启恢复、超预算结果标记、无效行号、范围改变、失败重复查询不回退旧结果，以及既有查询、会话、审计与呈现回归。保留2个既有框架警告（Starlette弃用提示、busy会话拒绝路径的协程提示），不影响本批断言。


访问 http://localhost:38080 。代码包继续按用户要求携带已配置API Key的.env，不用复制示例文件。不要执行down -v删除会话卷。

升级后先新建会话测试本批链路。旧版本未写入的助手历史不能声称已经完整恢复；本批重启测试证明的是新版已经保存的会话能恢复。

这6项是针对本次缺陷的回归，不代表任意问法100%正确。SQL人员字段与并列口径通过模型提示约束及真实结果验收，没有额外模型检查、自动重试或通用SQL重写器。长对话达到阈值时原生压缩可能增加摘要调用，本批短会话没有触发该阈值。极长会话压缩质量、容器实机和浏览器最终验收仍未完成。

结果呈现仍只给解释模型前20行预览，所以对34行的自然语言总结可能保守；完整34行已在结构化结果中，本批没有跨职责修改呈现模块。响应速度仍需后续优化，最终普通查询耗时约37–45秒。

框架依据：本机安装的AgentScope 2.0.8公开API与源码；[AgentScope官方能力说明](https://docs.agentscope.io/)列出原生上下文压缩、卸载与注入能力。

# 准确率优先：模型选择与语义一致性改造验收

2026-09-15 · Plan v1.12

结论：问题理解值得使用 qwen3.7-plus，已将默认配置切为“理解 Plus、SQL Plus、解释 Flash”。正常非空查询仍最多3次模型调用，不增加评审模型、自动重试或深度思考。模型能力与程序约束共同负责正确率，换型号不能替代范围绑定和契约修复。

## 模型选择的证据

使用相同代码、提示词、目录和10个固定输入，每个模型每题一次真实调用，并发2。只比较理解与真实SQLite实体绑定，不把它称为最终答案准确率；O03使用双方相同的人工核对历史上下文。没有调用评审模型。

| 模型 | 结构有效 | 理解与绑定符合需求 | 平均耗时 | 中位耗时 | 最长耗时 |
|---|---:|---:|---:|---:|---:|
| qwen3.8-flash | 9/10 | 8/10 | 3.376秒 | 2.502秒 | 10.733秒 |
| qwen3.7-plus | 9/10 | 9/10 | 7.800秒 | 3.754秒 | 37.920秒 |

Flash的一个额外业务错误是把主品牌条件改写为副品牌，目录中这两个字段独立存在；另一个失败是缺数据分支的结构一致性错误。Plus失败是模型生成的内部引用名不满足key格式要求，属于应由代码承担的字段设计问题。不能从10个样本推出所有场景的统计性优势，但按当前准确率优先的要求，选择Plus作为理解默认模型更合适。该选择保留环境变量覆盖能力。

这轮比较之前还保留了一次完整A/B诊断：Plus大量返回空提示文案，被旧Schema当成整个理解失败。修正为由代码补齐默认展示文案后，才进行上表的同版本比较。没有挑选重跑中的最佳答案混算。证据分别在 validation-consistency/model-ab、model-ab-final；更早的嵌套Schema冒烟和中止的8题尝试也保留，不算最终验收。

A/B之后继续修正了两个通用问题：内部引用键由代码根据引用内容稳定生成；完整新问题直接保留用户原话，只对追问进行补全。这些改造同时适用于所有模型，因此最终联调收益不能全部归因于换Plus。

## 本次实际修改边界

仍是六个业务模块。改动集中在 question_understanding 和 query_execution，以及基础设施中的角色型号配置；新增dateparser依赖、测试、回放和文档。source_ingestion、data_preparation、semantic_catalog、answer_presentation及在线编排的业务实现没有改动。原Excel生成的数据库哈希不变。

| 所属模块 | 节点或契约 | 职责 |
|---|---|---|
| 问题理解 | build_understanding_context | 装配可信历史、当前目录和未完成轮次 |
| 问题理解 | resolve_followup | 显式候选选择零理解模型调用；自然语言追问交给理解节点 |
| 问题理解 | interpret_question | 一次AgentScope结构化输出，判断范围、承接追问、提取活动/人名原话 |
| 问题理解 | validate_requirements | 验证原话、轮次、可见字段和重复引用；不读库、不调用模型 |
| 问题理解 | classify_outcome | 输出固定状态和QuestionRequest；新问题保留原话，确认选择只沿未变对象继承 |

| 查询执行 | generate_sql | 一次AgentScope + LlamaIndex调用，只看到经绑定的关系和目录语义 |

| 查询执行 | package_result | 返回动态列、实际SQL、快照和resolved_scope，交给已有呈现模块 |

理解模块公开契约升级为 understanding-v2：对象提及含名称/局部日期的SourceQuote，不能把目录ID存在性当作用户确认。单对象有多个真实候选才澄清，完整日程直接作为集合。内部关联键不由模型生成，目录内部ID也不供模型自由挑选。

每个绑定生成独立查询关系；日期范围不会被全局塞进所有表，也不会把比例分母一起过滤。SQLGlot检查实际可达的CTE、子查询和别名作用域，未使用的CTE不能充当已使用实体的证据。品牌/国家、AND/OR、分组、比例等仍由原始完整问题与标准SQL表达，没有自建通用查询DSL。

所有节点都有公开输入输出和独立调用入口；模块通过public.py及端口交互。AgentScope原生SQLite会话持久化继续承担保存/恢复，不新增Redis或LangGraph。升级后新建会话，不承诺旧understanding-v1状态兼容，不删除旧SQLite文件。

## 审计与调用数：仍有未完成项

原20题运行中，O10、N04审计写入发生OperationalError，其中N04缺失全部3条模型阶段日志。因此实际保存的模型调用记录为50条；按正常分支推算应53次，后者是推算，不能冒充完整审计实测。新6题保存18条模型调用记录，每题3条。

新增6题的H01运行日志也出现audit_write_failed，但数据库最终有完整阶段行且logging_failed为0。这个不一致未查清，所以严格验收保守记5/6，不能仅凭表内标志声称日志完全可靠。下一批应由基础设施/审计处理写入失败与失败标记一致性，不更改业务算法或增加模型调用。

没有默认自动修复重试：普通非空问数理解1 + SQL1 + 解释1；空结果理解1 + SQL1；拒绝/缺数据只理解1；歧义在SQL生成前由实体解析反馈，显式选候选再提问时理解0。模型全部enable_thinking=false，AgentScope及底层客户端max_retries均为0。

## 节点、模块和恢复验证

全量测试收集158项：156项直接通过，另2项仍断言旧版“新问题会被改写”的文本。将这两项改为校验重启前后完整QuestionRequest相等后，分别对进程terminate/kill恢复定向复测，2项均通过。保留原失败记录和复测记录，没有把它描述成单次全量158 passed。

新增验证覆盖：日期解析、独立范围与全局分母、EXISTS/NOT EXISTS、CTE/别名、无用CTE绕过、伪造绑定、目录乱序和替换内部ID、同名全部与单人澄清、用户引用保留、内部键不依赖输出顺序、新问题不能被改写为另一字段，以及原生SQLite中保存候选→重启→零理解调用选择→再次重启→自然语言追问保留已选人的闭环。

五个理解节点已有完整JSON回放样例；ruff检查通过。验收后只调整了一处范围提示文案，移除用户界面的内部引用键；SQL及绑定契约未变。此处用真实SQLite的32条结果做了无模型封装回放，差异与证据见 post-evaluation-changes.json、release-display-replay.json。

## 已知边界和下一步

1. 先修审计SQLite写入及错误标记一致性；原20题中两条请求仍不能称严格闭环。
2. 解释超时此前出现过，本轮未复现，不等于根因已修复。结果仍先保存，失败只允许显式重试解释；后续按独立呈现模块处理。解释重复表格和范围表述仍可优化。
3. 日期解析目前接受明确月日/年月日及已验证中英文格式，缺年份依照数据候选年份唯一确定；“明天”“27日”等相对日期/缺月表达不在本轮完整支持范围。遇到不能唯一解析时停下，不猜。
4. SQL验证证明的是受支持的对象范围、只读和访问限制，不证明任意自然语言与任意复杂SQL逻辑完全等价。别名未配置或名称近似匹配不能静默确认。
5. 此次没有验证Docker实机、手机/桌面浏览器视觉、PostgreSQL或飞书接入；不把SQLite联调当作这些阶段通过。
